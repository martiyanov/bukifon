# ESP32 для Букифона: что реально тянет, а что нет

Вопрос заказчика: «можно ли проект сделать на ESP32?» Короткий ответ: **да, но не любой
ESP32 и не в полном объёме «как Elektron»**. Ниже — расчёт и сравнение.

## 1. Сколько вообще нужно вычислений

Оценка в операциях с плавающей точкой на семпл (44.1 кГц), без оптимизаций:

| Задача | Нагрузка | Итог |
|---|---|---|
| 8-голосный 4-оп FM + 2 ZDF-фильтра + 4 огибающих | ~70–120 оп/семпл/голос | 8 × 100 × 44 100 ≈ **35 MFLOP/s** |
| Сведение 8 стерео-дорожек + 2 insert-FX на дорожку (простой FX) | ~50–150 оп/семпл/канал | 8 × 2 × 100 × 44 100 ≈ **70 MFLOP/s** |
| Time-stretch/pitch-shift (WSOLA/грануляр) на дорожку | ~50–150 оп/семпл/канал | +**35–100 MFLOP/s** |
| UI (800×480, 30 fps), энкодеры, секвенсор, файлы | — | 10–30 % одного ядра |

Итого «всё сразу» ≈ **150–200 MFLOP/s** + UI. Это немного по современным меркам:
важны не мегафлопсы, а **FPU, PSRAM и DMA**.

## 2. Кандидаты

| Платформа | CPU | RAM | FPU/DSP | Экран 800×480 | Вывод |
|---|---|---|---|---|---|
| **RP2040** (сейчас) | 2× M0+ 133 МГц | 264 КБ SRAM, без PSRAM | **нет FPU** | SPI, медленно (10–20 fps) | только прототип управления; DSP в fixed-point, RAM впритык (уже 80 %) |
| **ESP32-S3** | 2× Xtensa LX7 240 МГц | 512 КБ + 8 МБ PSRAM (octal) | FPU, SIMD-инструкции для int8/int16 | RGB parallel (LCD_CAM) 16 бит | **рабочий вариант v1.0**: синтез — легко, сэмплер — с ограничениями |
| **ESP32-P4** | 2× RISC-V 400 МГц + LP-ядро | 768 КБ + до 32 МБ PSRAM | FPU | MIPI-DSI/RGB, H.264 | **лучший вариант под сэмплер + большой экран**; но платформа молодая |
| **STM32H7** | 1× M7 480 МГц | 1 МБ + SDRAM | FPU + DSP-инструкции | LTDC RGB | отлично для DSP, но экосистема/цена/платы сложнее |
| **Teensy 4.1** | M7 600 МГц | 1 МБ + 8 МБ PSRAM | FPU + DSP | нет RGB (только SPI) | отлично для синтеза, плохо для 5″ экрана |

## 3. Практические ограничения ESP32-S3

1. **PSRAM и DMA.** I2S-DMA не умеет читать напрямую из PSRAM на S3 без копирования:
   звук надо гонять блоками PSRAM → внутренний SRAM → I2S. Это решаемо
   (двойная буферизация по 1–4 КБ), но добавляет задержку и код.
2. **Экран.** 800×480 RGB565 = 750 КБ на кадр. Внутренней SRAM (512 КБ) не хватает —
   кадр лежит в PSRAM. При 30 fps нужно ~37 МБ/с на чтение PSRAM; octal-PSRAM S3 даёт
   до ~80 МБ/с теоретически, реально 30–50 МБ/с → **30 fps достижимо**, 60 fps — нет.
   Для 60 fps и тяжёлого UI лучше ESP32-P4.
3. **USB.** S3 имеет USB-OTG (Full-Speed 12 Мбит/с): USB-MIDI и USB-audio class 2
   (2 in / 2 out) — реально; 8 каналов audio class — нет (Full-Speed не потянет).
4. **Сэмплер.** 8 стерео-дорожек в PSRAM 8 МБ — это ~45 с при 44.1/16; потоковая
   подгрузка с SD (SPI/SDIO) позволяет играть длинные сэмплы. Time-stretch —
   упрощённый (WSOLA), не «как у Digitakt».

## 4. Ответ по режимам

| Режим | ESP32-S3 | ESP32-P4 |
|---|---|---|
| 8-голосный FM-синтез + фильтры | ✅ полностью | ✅ с запасом |
| Wavetable, 3D-мод-матрица, секвенсор | ✅ | ✅ |
| Сэмплер 8 стерео-дорожек | ⚠️ 4–6 дорожек комфортно, 8 — на пределе | ✅ 8 дорожек |
| Time-stretch / pitch-shift | ⚠️ упрощённый | ✅ нормальный |
| 2 insert-FX на дорожку | ⚠️ 1–2 простых FX | ✅ |
| Экран 800×480 | ⚠️ 25–30 fps | ✅ 60 fps |
| USB audio 2×2 | ✅ | ✅ (HS) |
| Пользовательские DSP-модули | ✅ C++ (статические) + Lua | ✅ |

## 5. Варианты архитектуры

- **A. Один ESP32-S3** — дешево (~10–15 $), один чип, синтез полноценный, сэмплер
  урезан. Подходит для v1.0 «синтезатор + сэмплер-лайт».
- **B. Один ESP32-P4** — ~15–25 $, сэмплер и экран полноценные; нужен внешний
  Wi-Fi/BT модуль (C6) только если нужен беспровод; USB HS. Рекомендуется для v1.1.
- **C. Два чипа: ESP32-S3 (UI/IO/секвенсор) + DSP (ADAU1467 или SHARC)** — как у
  Elektron; +30–60 $ и заметно больше сложности; имеет смысл только в v2.
- **D. FPGA** — не нужно: аналоговые голоса у нас отдельными модулями, цифру
  проще сделать на MCU.

## 6. Поправки второго мнения (ревью)

Полный разбор — [docs/03-second-opinion-mcu.md](03-second-opinion-mcu.md). Ключевые поправки к моей первой версии:

1. **USB.** 8 каналов out + 8 in @48/24 = **2.3 МБ/с = 18.4 Мбит/с**; у Full-Speed потолок ~9.8 Мбит/с.
   Значит **UAC2 multichannel требует High-Speed**: ESP32-P4 / STM32H7 / Teensy. На S3 — только стерео 24/48.
2. **Экран.** 800×480 RGB565 = 750 КБ; SPI 80 МГц = 10 МБ/с → **13 fps** на полную перерисовку
   (30 fps — только при <40 % изменённых пикселей; волна/осциллограф не тянет). Нужны **DSI (P4)**
   или **LTDC+DMA2D (H7)**.
3. **PSRAM.** Измерено на S3: чтение **88 МБ/с**, запись 49 МБ/с; flash и PSRAM делят MSPI.
   Для 8 стерео-гранул нужно 30–70 МБ/с + 7 МБ/с дисплей → запаса нет.
4. **Бюджет.** Синт 8×4-op FM ×2 OS + ladder + 4 env = 55–80 MMAC/s; сэмплер 8 стерео = 30–45;
   UI 800×480@30 = 15–30 % ядра. Итог: S3 60–85 % без запаса; **P4 35–50 %**; H743 35–45 %.
5. **Предел памяти.** 8 стерео × 30 с = 46 МБ — не влезает даже в 32 МБ PSRAM.
   Резать по порядку: 8 стерео → **8 моно** (Digitakt MKI был моно!), 2 insert → 1 insert + 2 send,
   time-stretch → только гранулярный (phase vocoder +8–12 недель), 48→44.1 кГц экономит лишь 8 %.
6. **DSP/FPGA в v1 не брать:** ADAU1701/1467 не имеют памяти сэмплов (сэмплер не могут),
   SHARC 21569 = 9–12 мес на порт, Spartan — это I/O, не DSP.
7. **Модули:** на S3/P4 нет MMU → «.so» не песочница. Аудио-рейт — статический C++ в прошивке;
   control-rate — Lua (1 кГц/UI/секвенсер); полная изоляция — свой MCU в картридже.

## 7. Вердикт (обновлён)

| Платформа | Что тянет | Когда брать |
|---|---|---|
| **ESP32-P4** (32 МБ PSRAM, HS USB, DSI) | 8 моно-дорожек + 8 голосов + 800×480 + UAC2 с запасом 2–3× | **основной кандидат v1.0** после бенчмарка |
| **ESP32-S3** (8 МБ PSRAM) | 8 моно, 6 голосов, экран 30 fps с частичной перерисовкой, USB-стерео | только если бюджет жёстко ограничен |
| **STM32H743** | то же, что P4, но тулчейн/платы дороже | альтернатива при дефиците P4 |
| **RP2040 / RP2350** | I/O-сопроцессор (CV/шина/сканы), не звук | оставить в схеме |

**Следующий шаг — не заказ плат, а 2 недели бенчмарка** на P4/S3/H7 с гранулярным чтением
PSRAM (не memcpy) и реальным фреймбуфером 800×480. После этого — «cut-list» и фиксация
требований, и только потом rev.3.
